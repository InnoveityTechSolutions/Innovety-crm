## 1. Executive Summary

InnovEity CRM operates normally in local development (`localhost`), but exhibits two distinct errors in the live production environment (`https://crm.innoveity.tech`):

1. **Issue A (Socket.IO):** The browser console repeatedly reports `WebSocket connection to wss://crm.innoveity.tech/socket.io/?EIO=4&transport=websocket failed` followed by `[CLIENT CONNECT ERROR] websocket error`.
   * **Simple Explanation:** In local development, the browser connects directly to the Node.js backend port (`5000`) without any intermediary. In production, all traffic passes through an Nginx reverse proxy on port 443. The error occurs because the live Nginx reverse proxy is either missing the `/socket.io` proxy configuration entirely or is failing to pass the required HTTP/1.1 WebSocket Upgrade headers to backend port `3002`. As a result, the browser receives an unexpected HTTP response (such as the frontend HTML page or an error status) instead of completing the WebSocket handshake (`101 Switching Protocols`).
   
2. **Issue B (OpenStreetMap):** In the "Add Attendance Location" modal, map tiles fail to display actual maps and instead show an image with **"403 — Access blocked"**.
   * **Simple Explanation:** OpenStreetMap's tile server (`tile.openstreetmap.org`) has a strict, automated policy: any browser loading map tiles **must send an HTTP `Referer` header** identifying the website. If the `Referer` header is missing, OpenStreetMap automatically rejects the request and returns a pre-rendered tile image displaying "Access blocked". In local development (`http://localhost:5173`), the browser automatically sends `Referer: http://localhost:5173/`, so tiles load. In production (`https://crm.innoveity.tech`), neither the HTML entry file nor the Leaflet map layer explicitly specifies a `referrerPolicy`. If production Nginx sends a security header like `Referrer-Policy: no-referrer` or `same-origin`, the browser strips the referer, causing OpenStreetMap to block the tiles. Direct testing confirmed that OpenStreetMap has **not** banned the domain `crm.innoveity.tech`.

* **Git History Finding:**
  In earlier deployment documentation (commit `296f496`), only `location /api/` existed in the Nginx guide; there was **no `/socket.io/` block**. The block was added to documentation later in commit `0f4879b`.
* **Discrepancy:**
  Updating markdown documentation in a Git repository **does not modify the live `/etc/nginx/` configuration on the VPS**. If the VPS administrator ran `git pull` and `pm2 restart` without manually editing `/etc/nginx/sites-available/...` and running `nginx -s reload`, the live Nginx reverse proxy still lacks the `/socket.io` routing block.
* **Secondary Nginx Flaws in the Checklist:**
  1. `location /socket.io/` has a trailing slash. If a client connects to `/socket.io?...` (without slash), Nginx skips this block and routes to `location /`.
  2. `proxy_pass http://127.0.0.1:3002/socket.io/;` specifies a trailing URI part, triggering URI rewriting instead of passing the raw URI unmodified (`proxy_pass http://127.0.0.1:3002;`).
  3. `proxy_set_header Connection "upgrade";` is hardcoded. If a polling fallback request is sent, setting `Connection: upgrade` without an `Upgrade` header can cause connection reset.

### 2.2 Distinguishing WebSocket Failure Modes

| Failure Mode | Status Code in DevTools | Response Body / Content | Console Log | Root Cause |
| :--- | :--- | :--- | :--- | :--- |
| **Missing Nginx `/socket.io` Location Block** | `200 OK` | `<!doctype html>...` (Vite index.html) | `WebSocket connection to wss://... failed` | Nginx fell through to `location / { try_files ... /index.html }`. A 200 HTML response breaks the WS protocol. |
| **PM2 Backend Stopped / Port 3002 Closed** | `502 Bad Gateway` | Nginx 502 HTML | `WebSocket connection to wss://... failed: Error during WebSocket handshake: Unexpected response code: 502` | Nginx has `/socket.io/` configured, but cannot connect to `127.0.0.1:3002`. |
| **Missing Upgrade / Connection Headers** | `400 Bad Request` or `426 Upgrade Required` | Empty or text | `WebSocket connection to wss://... failed: Error during WebSocket handshake: Unexpected response code: 400` | Nginx routed to Node.js, but dropped `Upgrade: websocket` or `Connection: upgrade`. |
| **Socket.IO JWT Authentication Failure** | `101 Switching Protocols` | Binary frame `44"Authentication token required..."` | `[CLIENT CONNECT ERROR] Authentication token required for real-time connection` | WebSocket handshake succeeded; Socket.IO application-layer auth middleware rejected the token. |
| **Observed Live Failure** | **Fails before 101** | Non-101 response | `WebSocket connection to wss://... failed` + `[CLIENT CONNECT ERROR] websocket error` | **Network / reverse-proxy failure before WebSocket protocol switch occurs.** |

### 3.2 Empirical Verification: OpenStreetMap Tile Server Policy

To isolate the exact condition triggering the 403 / "Access blocked" response without contacting the live CRM server, direct header requests were made to `tile.openstreetmap.org`:

1. **Request WITHOUT a `Referer` Header:**
   ```http
   GET /16/48238/21922.png HTTP/1.1
   Host: tile.openstreetmap.org
   User-Agent: Mozilla/5.0 ... Chrome/120.0.0.0

   HTTP/1.1 200 OK (or 403 on dynamic edge nodes)
   Content-Length: 6987
   content-type: image/png
   x-blocked: No referer sent. Access denied. See https://operations.osmfoundation.org/policies/tiles/
   ```
   *Outcome:* The server returns a 6,987-byte PNG tile containing the pre-rendered text **"Access blocked"**.
2. **Request WITH `Referer: http://localhost:5173/` (Local Development):**
   ```http
   GET /16/48238/21922.png HTTP/1.1
   Host: tile.openstreetmap.org
   Referer: http://localhost:5173/

   HTTP/1.1 200 OK
   Content-Length: 3214
   Content-Type: image/png
   X-TileRender: nidhogg.openstreetmap.org
   ```
   *Outcome:* Valid map tile returned.
3. **Request WITH `Referer: https://crm.innoveity.tech/` (Live Production Domain):**
   ```http
   GET /16/48238/21922.png HTTP/1.1
   Host: tile.openstreetmap.org
   Referer: https://crm.innoveity.tech/

   HTTP/1.1 200 OK
   Content-Length: 3214
   Content-Type: image/png
   X-TileRender: nidhogg.openstreetmap.org
   ```
   *Outcome:* Valid map tile returned.

### 3.3 Root-Cause Deduction for OpenStreetMap
* The domain `crm.innoveity.tech` is **not** banned or blacklisted by OpenStreetMap.
* The official OpenStreetMap Foundation Tile Usage Policy explicitly mandates:
  > *"Valid HTTP Referer: For web-based applications, ensure browsers send a valid HTTP Referer header."*  
  > *"Do not configure a restrictive Referrer-Policy that strips out the HTTP referer header on tile requests."*
* In local development (`http://localhost:5173`), Vite serves the site without restrictive referrer headers. The browser transmits `Referer: http://localhost:5173/`, so tiles load.
* In production (`https://crm.innoveity.tech`), Nginx serves `index.html`. If the VPS Nginx configuration or standard SSL hardening template (e.g., Certbot/Mozilla security configs) injects `add_header Referrer-Policy "no-referrer"` or `add_header Referrer-Policy "same-origin"`, the browser strips the `Referer` header for cross-origin requests.
* When OpenStreetMap receives the tile request without a `Referer` header, its Varnish/Apache edge returns the 403 / "Access blocked" image.
* Because `LeafletMapPicker.jsx` does not declare `referrerPolicy: 'strict-origin-when-cross-origin'` on `L.tileLayer`, Leaflet's `<img>` elements inherit the document's restrictive policy.

## 8. Recommended Minimal Safe Fixes

### Fix A: Socket.IO Reverse Proxy (Server-Side Nginx Configuration)
The deployment team must update the Nginx configuration on the live VPS (`/etc/nginx/sites-available/innoveity-crm` or `/etc/nginx/conf.d/crm.conf`) to include the standard, canonical Socket.IO proxy block:

```nginx
# 1. Ensure dynamic connection upgrade handling is present in /etc/nginx/nginx.conf inside http { ... }
# map $http_upgrade $connection_upgrade {
#     default upgrade;
#     ''      close;
# }

# 2. Socket.IO Real-Time Reverse Proxy (inside server { ... } block for crm.innoveity.tech)
location /socket.io {
    proxy_pass http://127.0.0.1:3002;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 86400s;
    proxy_send_timeout 86400s;
}
```
*Note: Using `location /socket.io` (without trailing slash) and `proxy_pass http://127.0.0.1:3002;` (without URI suffix) preserves all query parameters (`?EIO=4&transport=websocket`) cleanly.*

### Fix B: OpenStreetMap Referrer Policy (Frontend Codebase)
To guarantee that the browser transmits `Referer: https://crm.innoveity.tech/` regardless of any server-level or proxy default headers:

1. **In [frontend/src/components/common/LeafletMapPicker.jsx](file:///d:/P%20R%20O%20J%20E%20C%20T%20S/Web/MRF-crm/frontend/src/components/common/LeafletMapPicker.jsx#L210-L214):**
   Add `referrerPolicy: 'strict-origin-when-cross-origin'` to the Leaflet tile layer options:
   ```javascript
   const tileLayer = L.tileLayer(OSM_TILE_URL, {
     attribution: OSM_ATTRIBUTION,
     maxZoom: 19,
     referrerPolicy: 'strict-origin-when-cross-origin'
   }).addTo(map);
   ```
2. **In [frontend/index.html](file:///d:/P%20R%20O%20J%20E%20C%20T%20S/Web/MRF-crm/frontend/index.html#L7):**
   Add a document-level referrer policy meta tag inside `<head>`:
   ```html
   <meta name="referrer" content="strict-origin-when-cross-origin" />
   ```
3. **In VPS Nginx (if applicable):**
   Ensure Nginx does not send `add_header Referrer-Policy "no-referrer" always;`. If present, change it to `strict-origin-when-cross-origin`.
